## 0. 一句话方案

自定义风格 = **8 个已验证布局原语 × 用户参数**（色板/装饰/字体角色/文案语气），服务端白名单校验 + 快照入版本，Agent 可增量创建、用户独占管理，预览与渲染同口径占配额。

## 1. 核心设计决策及理由

**为什么用组合式而不是自由定义**：勘察 `renderer/render.mjs` 发现 8 个风格是 8 个手写布局函数，recipe 字段从未被通用解释（第 16 行直接拒绝未注册风格）。自定义风格的可靠路径是**参数化已有原语**而非新增渲染能力：

| 决策 | 选择 | 理由 |
|---|---|---|
| 布局 | 复用 8 个 base_layout，不新增 | 零新增布局代码；每个布局的越界检查已被 40+ 渲染用例覆盖 |
| 色板 | 用户自选 2–5 色（hex 白名单校验） | 视觉自由度的主要来源；渲染端二次校验 |
| 装饰 | 每布局独立的装饰白名单内多选 | 防止"贴纸布局用票据装饰"的穿帮组合 |
| 字体 | 4 种字体角色枚举 | 渲染端只有 Noto Sans SC 一个字重——角色以字号/字距/加粗近似，未来加字体可无损升级 |
| 文案语气 | ≤80 字自由文本，只影响模型 | 与内置 registry 的 copy_tone 同机制（`styles.context()` 注入模型上下文） |

**为什么 Agent 只创建不修改**：风格是用户品味的沉淀，被模型悄悄改掉比"创建一个新风格"的冒犯感高一个量级；且风格上限 3 个，模型创建前必须征得用户意图（用户说"换个粉色系的"才创建）。修改/删除走 UI 显式操作，与 `save_preference` 模型不可调用的权限哲学一致。

## 2. 分层架构影响（对照 MVP 七层）

```
① 交互层   React SPA：风格网格分「内置/我的」两区 + 创建/编辑/预览表单 + 删除两步确认
② 产品层   +5 个路由（见 §4）；CardInput/Revison 的 style 校验扩展自定义 ID
③ 编排层   CARD_TOOLS + create_style；get_style_context 返回自定义风格；worker 新增 preview 分支
④ 模型层   不变（DeepSeek 工具调用协议不变）
⑤ 能力层   styles.py 扩展（校验/快照/上下文）；render.mjs 布局函数参数化 + 自定义 theme 解析
⑥ 数据层   +user_styles 表；versions.style_snapshot 已预留，承载自定义 recipe
⑦ 基建层   不变
```

## 3. 数据模型

```sql
CREATE TABLE user_styles (
  id TEXT PRIMARY KEY,            -- u_ + 8位hex，与内置 ID 永不冲突
  user_id TEXT NOT NULL,
  name TEXT NOT NULL,             -- ≤40字
  recipe TEXT NOT NULL,           -- StyleRecipe JSON（白名单校验后入库）
  created REAL NOT NULL
);
CREATE INDEX user_styles_owner ON user_styles(user_id);
```

- **≤3 强制点**：POST / create_style 插入前 `SELECT COUNT(*)` 检查，满则 409 / ToolError
- **历史卡不可变**：版本存 `style_snapshot`（schema 已预留 `StyleSnapshot{ id, name, registry_version, recipe }`）；渲染只认快照不认 user_styles 行——**风格后续改/删，历史版本重渲染结果不变**（这是快照设计的核心收益）
- 自定义风格 snapshot 的 `registry_version` 沿用注册表版本号（recipe 结构同源）

## 4. API 契约（产品层新增 5 路由）

| 路由 | 请求 → 响应 | 副作用 / 鉴权 |
|---|---|---|
| `GET /api/styles` | → `{built_in:[...], mine:[≤3]}` | 只读本身份 |
| `POST /api/styles` | `{name, recipe}` → `{id}` | 创建；≥3 返回 409；recipe 白名单校验 |
| `PUT /api/styles/{id}` | `{name?, recipe?}` → `{ok}` | 仅本人；历史版本不受影响 |
| `DELETE /api/styles/{id}` | → `{ok}` | 仅本人；前端两步确认；历史版本不受影响 |
| `POST /api/styles/preview` | `{recipe}` → `{task_id}` | **占 1 次每日配额**；入队 kind='preview' 任务 |
| `GET /api/previews/{task_id}/page-01.png` | → PNG | 仅本身份；预览产物存 `data/previews/{task_id}/` |

预览任务（worker 新分支，不调模型）：固定示例文案（标题"今日精神状态"等）+ 用户 recipe 组成快照 → 直调渲染器 → PNG 落盘。复用 `enqueue` 的排队/重试/重启恢复；`task_kind != 'inspect'` 自动计配额，与 PRD"预览占配额"一致，无需额外代码。

## 5. 工具契约（编排层增列）

| 工具 | 输入 → 输出 | 权限与副作用 |
|---|---|---|
| `create_style`（新增） | 名称 + StyleRecipe → `{id, remaining}` | 仅创建；≤3 满则报错并提示用户删除旧风格；**不能修改/删除任何风格**；recipe 白名单校验；写 user_styles 表 |

既有工具变更：
- `get_style_context`：返回 `styles`（内置）+ `mine`（本人自定义：id/name/copy_tone/recipe 摘要）
- `render_card`：`styles.snapshot(style)` → `styles.snapshot(style, user_id)`；自定义 ID 非本人所有时抛 ToolError（模型收到错误回喂）；payload 风格强制逻辑不变

**recipe 白名单**（后端 `styles.validate_recipe`，渲染端二次校验）：
- `base_layout` ∈ 8 个注册值（editorial / sticker-stack / minimal-poster / receipt / notebook / night-grid / soft-diary / archive-grid）
- `palette`：2–5 个 hex 色（`^#[0-9a-fA-F]{6}$`，入库前归一小写）
- `decoration`：⊆ 所属布局白名单（editorial: orb/fine-line；sticker-stack: label/tilt；minimal-poster: rule；receipt: perforation/serial-number/stamp；notebook: tape/scribble/note；night-grid: neon-orb/grid/signal；soft-diary: soft-orb/frame；archive-grid: grid/index/data-block）
- `typography` ∈ {display-sans, editorial-serif, friendly-sans, mono-editorial}
- `copy_tone` ≤80 字自由文本

## 6. 渲染器改造（能力层，风险最高处）

**两步走，金样锁定**：

1. **纯重构**：8 个布局函数 `card(c)` → `layout(c, theme)`，theme 默认取注册表 recipe。**验收：重构前后 8 个内置风格 PNG 哈希逐字节一致**（render.test.mjs 金样回归）。渲染逻辑零行为变化后才进入第 2 步。
2. **接自定义**：`render()` 解析 `content.style_snapshot.recipe`——存在则按 `base_layout` 选布局函数 + 传入用户 theme；快照结构/白名单在渲染端独立再校验一次（纵深防御）；无快照或快照非法则拒绝。

布局选择从"style ID 查表"改为"base_layout 查表"：内置卡也走同一入口（theme 来自服务端注入的快照），消除两套路径。

## 7. 系统提示词 diff（CARD_SYSTEM）

现有提示词追加一段：

> 可用风格包括内置风格和用户的自定义风格（ID 以 u_ 开头），风格上下文中有每个风格的说明与文案语气。用户明确要求新风格时，用 create_style 创建（每人最多 3 个；已满时告知用户需要先删除旧风格）；你不能修改或删除任何风格。自定义风格与内置风格一样通过 render_card 使用。

## 8. 上下文与记忆策略

- **不变**：仍零长期人格沉淀（PRD 决策 8）；风格数据是工具数据，不做画像
- 自定义风格随 `get_style_context` 进入模型上下文（每任务一次，惰性、有界：≤3 个 × recipe 摘要）
- 跨会话"记住风格"继续走现有 preferences 机制（单选默认风格），模型无权写

## 9. 权限与安全边界

- 风格 ID 命名空间隔离：`u_[0-9a-f]{8}` vs 内置短词，注入不可能
- 所有权逐请求校验（GET/PUT/DELETE/preview 均绑定 user_id）
- recipe 双重白名单（后端 + 渲染端）；**任何用户输入都不可能成为 CSS/SVG/URL**——渲染器只收到服务端构造的快照
- 渲染器仍只监听回环 + token 鉴权，自定义渲染不扩大攻击面
- 预览任务与生成任务同一鉴权与配额体系

## 10. 可观测性

- traces 新增 `style` 事件（创建/预览，记录 ok/ms），不记录 recipe 内容（recipe 含用户输入，属隐私边界，与"日志不含提示词"原则一致）
- 既有 model/tool/task 遥测不变；自定义风格成功率可用 traces 推导

## 11. 前端改动（单文件 SPA 内增量）

- 风格选择网格：「内置」8 张 +「我的」区（≤3 张，含新建入口卡片）
- 创建/编辑表单：布局 8 选 1（用现有 `frontend/public/samples/` 缩略图）→ 色板（2–5 个取色器 + 6 组预设色片）→ 装饰多选 chips（随布局切换白名单）→ 语气输入 → 名称
- 预览按钮：调 preview 接口 → 轮询任务（复用现有 1.5s 轮询组件）→ 显示 PNG；按钮旁常驻"预览占 1 次额度"提示
- 删除两步确认（复用作品删除的交互）
